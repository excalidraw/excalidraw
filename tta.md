# TTA (text-to-anything) review

Reviewed 2026-06-12, branch `dwelle/tta` (client: `packages/excalidraw/TTA/*`, app wiring in `excalidraw-app/components/AI.tsx`; server: `excalidraw-plus/libs/server/tta/**` + consumers `apps/api/src/routes/ai.ts`, `apps/oss-ai-server/src/api/ai.ts`).

**Overall**: the feature is in good shape. The streaming pipeline (eager provider start overlapping the attempt persist, partial EXML parse → skeleton snapshots, client preview insert/commit with the NEVER→IMMEDIATELY undo dance) is well thought out and documented in the right places. Zod validation exists at the route boundary, the parser has hardening caps (1M chars / 128 depth / 10k nodes), and ID remapping is chat-namespaced and deterministic so streamed re-parses update elements in place. The issues below are mostly lifecycle edges (disconnects, stops, retries, concurrency) rather than core-design problems.

Legend: 🔴 bug, should fix before release · 🟡 should fix / verify · 🔵 improvement / polish

## 1. High-priority bugs

### 🔴 C1 — Enter-to-send bypasses `isSending` → concurrent generations
[TTAComposer.tsx:203-248](packages/excalidraw/TTA/TTAComposer.tsx#L203-L248) — `handleSend` only checks `disabled`; `canSend` (which includes `!isSending`) gates the **button** only. Pressing Enter while a generation is streaming sends a second prompt. `sendChatPrompt` ([TTADialog.tsx:730](packages/excalidraw/TTA/TTADialog.tsx#L730)) has no `isSendingChat` guard either, and `generateResponse` overwrites `activeStreamAbortControllerRef` ([useAIStreamingLifecycle.ts:191-192](packages/excalidraw/TTA/useAIStreamingLifecycle.ts#L191-L192)), so the first stream becomes uncancellable, two streams patch two assistant messages concurrently, the canvas draft thrashes between message ids, and the user double-spends rate limit.

Fix: guard `handleSend` with `isSending`, and (belt-and-braces) make `sendChatPrompt`/`generateResponse` single-flight (return early or auto-cancel the previous stream). **Implementation proposal: [tta_c1.md](tta_c1.md).**

### 🔴 C2 — Mid-stream disconnect is reported as a successful “empty response” and wipes the streamed preview
[client.ts:314-324](packages/excalidraw/TTA/client.ts#L314-L324) — if the SSE stream ends without a `done`/`error` event (proxy idle timeout, server crash, clean close on lambda timeout), the client returns `finalPayload: { skeletons: [], isComplete: true }`. The lifecycle then overwrites the partial `skeletons` accumulated on the message, shows “empty response”, and `applyStreamingCanvasPreviewResult([], isComplete)` **clears the on-canvas preview** ([useAIStreamingLifecycle.ts:300-334](packages/excalidraw/TTA/useAIStreamingLifecycle.ts#L300-L334), [useAIStreamingCanvasPreview.ts:206-213](packages/excalidraw/TTA/useAIStreamingCanvasPreview.ts#L206-L213)).

Fix: treat EOF-without-`done` as an error, keep the partial skeletons on the message, and offer Retry. The server in fact already terminates every deliberately-ended stream with a `data: [DONE]` sentinel (`StreamingResponse.end()` in `libs/server/fastifyutils/src/lib/streaming.ts`) — but `iterateSSEJSONChunks` silently `break`s on it, so the client discards the very signal that distinguishes “server ended deliberately” from “connection cut”. Surface it and require `done|error` for success. **Implementation proposal: [tta_c2.md](tta_c2.md).**

### 🔴 C3 — Failed retry throws an unhandled promise rejection
[TTADialog.tsx:1016-1036](packages/excalidraw/TTA/TTADialog.tsx#L1016-L1036) — `handleRetry` has `try { await streamAssistantResponse(...) } finally {...}` with **no catch**, and its call site is a floating promise. `generateResponse` intentionally re-throws a handled-marked error after patching the message ([useAIStreamingLifecycle.ts:371-373](packages/excalidraw/TTA/useAIStreamingLifecycle.ts#L371-L373)); `sendChatPrompt` catches it, `handleRetry` doesn’t. Precision (from the proposal’s deeper verification): most transport failures *resolve* as `{ error }` (`TTAStreamFetch` is total) and never reject — the rejecting paths are final-canvas-render failures (`INVALID_RESULT`), custom host adapters whose `stream()` rejects, and pre-stream guard throws (which additionally leave the retry bubble spinning forever). Mirror the `sendChatPrompt` catch (`isAIChatErrorHandled`), patching the existing retry bubble rather than appending. **Implementation proposal: [tta_c3.md](tta_c3.md).**

### 🔴 C4 — `getViewportCenter` mishandles canvas offset (library embeds insert off-center)
[insertAISkeletons.ts:24-45](packages/excalidraw/TTA/insertAISkeletons.ts#L24-L45) computes `(width / 2 - offsetLeft) / zoom - scrollX`. The canonical transform is `x = (clientX - offsetLeft) / zoom - scrollX` with viewport-center `clientX = offsetLeft + width / 2`, i.e. the correct value is `(width / 2) / zoom - scrollX` — `offsetLeft` cancels out (see `viewportCoordsToSceneCoords`, [packages/common/src/utils.ts:449-451](packages/common/src/utils.ts#L449-L451)). On excalidraw.com (`offsetLeft = 0`) this is invisible; for any host embedding the editor with a left/top offset, generations land shifted by `offset/zoom` scene units (= `offset` screen px) left/up of center. Also drop the `as ... & { offsetLeft?: number }` cast — these exist on `AppState`. **Implementation proposal: [tta_c4.md](tta_c4.md)** (also flags 2 pre-existing unrelated failures in insertAISkeletons.test.ts on this branch).

### 🔴 S1 — Generation attempts stuck `pending` in DB on client stop/disconnect and on generic errors
`streamTta` (`tta.ts:1996-2308`) marks aborts only at explicit `signal?.aborted` checkpoints, and there is **no `finally`**. When the consumer stops pulling (Plus route breaks out of `for await` on `stream.signal.aborted` — `apps/api/src/routes/ai.ts:555-558`), the generator receives `.return()` at the suspended `yield`: `catch` does not run, `markAttemptAborted` never executes. The eager-iterable’s own `finally` does cancel the provider request (good — no token leak), but the `tta_chat_turn_messages` row stays `pending` forever. Same for generic throws after `saveGenerationAttempt` (e.g. `saveGeneration` DB failure): outer catch yields a stream error but never marks the message `failed`.

Fix: wrap the body in `try/finally`; in `finally`, if the attempt was persisted and not completed, write the terminal status (the consumer-teardown default is `aborted`). (Status currently only matters for analytics and context-loading hygiene, but every user Stop producing a permanently-`pending` row will pollute any future “resume incomplete generation” work.) **Implementation proposal: [tta_s1.md](tta_s1.md)** — includes an empirical verification of the async-generator `.return()`/`finally` semantics the fix rests on.

### 🟡 S2 — Stop/abort refunds the rate limit unconditionally → cost-amplification loophole
`apps/api/src/routes/ai.ts:563-580` rolls back the rate-limit charge whenever the stream errored **or aborted**. A user can let the model stream 95% of the tokens, hit Stop, and repeat — each round consumes provider tokens but zero quota. Suggest refunding aborts only when nothing meaningful was streamed (e.g. no `partial` chunk yielded yet, or below a token threshold), keeping the refund for genuine server errors. Two aggravations found during proposal work (verified): the TTD `chat-streaming` route has the **identical** unconditional abort-refund against the same shared `textToDiagram` key (porting the fix there is a follow-up), and `rateLimiting.rollback` is a fire-and-forget Firestore decrement floored at 0 — not idempotent, so double-rollback paths refund someone else’s charge. **Implementation proposal: [tta_s2.md](tta_s2.md).**

### 🟡 S3 — Partial parsing is unthrottled on the non-additive path: O(n²) CPU + O(n²) SSE bytes
`tta.ts:2171-2186` re-runs `parsePartialExmlV1(accumulated)` and emits the **entire** skeleton array on every content delta. The additive path right above it throttles (250 ms / 256 chars — `tta.ts:2131-2168`), and `requestTtaFix` (`tta.ts:1517-1545`) is also unthrottled. For an 8k-token response with per-token deltas this is hundreds of full re-parses and a quadratic number of skeleton bytes on the wire (the client itself throttles rendering to 300 ms, so most frames are discarded anyway). Apply the same time+delta gating to all partial emissions; longer-term, consider emitting deltas/ops instead of full snapshots. **Implementation proposal: [tta_s3.md](tta_s3.md)** — one shared emit-gate (250 ms, first-attempt exception that also fixes the zero-partial small-edit finding from §5, byte-identical-snapshot dedupe), dissolving the L1 double-assignment along the way.

### 🟡 S4 — turn/message order assignment: race verified not-reachable today — but accidentally, fragilely, and without conflict handling
`saveGenerationAttempt` computes `coalesce(max(order),0)+1` via SELECT-then-INSERT (`tta.ts:1104-1151`). **Verification results** (see [tta_s4.md](tta_s4.md)): the unique constraints DO exist (`(chat_id, turn_order)` and `(turn_id, message_order)` unique indexes in both oss and plus schemas — verified), and the race is not reachable today because every writer transaction happens to *lead* with an `UPDATE tta_chats` (the `updated_at` touch), whose row lock serializes per-chat writers under read committed. That serialization is incidental and undocumented — reordering the transaction or batching the touch silently re-opens the race — and there is no 23505/40001 handling anywhere, so any drift surfaces as a masked generic 500. Fix: make the serialization explicit (`pg_advisory_xact_lock` keyed per chat — the repo already uses this pattern in `user-api-keys.ts`) plus a bounded retry on conflict codes. **Implementation proposal: [tta_s4.md](tta_s4.md).**

### 🔴 S5 — Plus TTA migration is journal-orphaned: CI migration would never create the tables (found during S4 verification)
`migrations/excalidraw-plus/0022_green_clint_barton.sql` (creates all Plus TTA tables) exists on disk but is **absent from `migrations/excalidraw-plus/meta/_journal.json`** — a master-merge collision left `0022_mushy_expediter` occupying idx 22. Drizzle migrates from the journal, so a Plus deploy of this branch runs zero TTA DDL and every TTA request 500s on missing tables (dev environments are masked by `db push`). Verified directly: journal idx 22 = `mushy_expediter`; `green_clint_barton` is referenced nowhere in the journal. tta_s4.md also flags schema↔migration column drift (`model` / `web_search_*`) to reconcile at the same time. Repair: regenerate the migration on a rebased branch (`pnpm nx db api generate`, per repo convention) — details in [tta_s4.md](tta_s4.md).

## 2. Medium

### Client

- 🟡 **M1 — Preview throttle has no trailing flush.** [useAIStreamingCanvasPreview.ts:278-313](packages/excalidraw/TTA/useAIStreamingCanvasPreview.ts#L278-L313) — a chunk arriving inside the 300 ms window is parked in `pendingStreamingCanvasPreviewResultRef` but no timer is scheduled; it renders only when the *next* chunk arrives or on final `flush()`. If the provider stalls mid-stream, the canvas freezes on a stale frame for the entire stall. Schedule a `setTimeout(remaining)` when parking a pending result (the message-list skeletons keep updating, so the chat preview and canvas can visibly diverge today).
- 🟡 **M2 — History persistence is whole-array, last-writer-wins.** [history.ts:13-35](packages/excalidraw/TTA/history.ts#L13-L35) stores *all* conversations under one `"all"` key; [useTTAChatHistory.ts:131-146](packages/excalidraw/TTA/useTTAChatHistory.ts#L131-L146) rewrites it (debounced 500 ms) on every change — including every streaming skeleton patch, since the auto-save effect keys off `chatMessages`. Two tabs clobber each other’s chats wholesale, and streaming triggers repeated large IndexedDB writes (full history incl. all skeleton payloads, serialized on the main thread). Suggest per-chat keys (save only the active chat), and a `BroadcastChannel` or load-merge-by-`updatedAt` for cross-tab safety.
- 🟡 **M3 — Hydration race can drop a just-created chat.** [useTTAChatHistory.ts:94-117](packages/excalidraw/TTA/useTTAChatHistory.ts#L94-L117) — `loadHistory()` resolving late **replaces** in-memory history; a chat created (and auto-saved into the atom) before hydration completes vanishes until its next message. Merge by id instead of replacing.
- 🟡 **M4 — `AIChatTruncateResponse.revision` doesn’t exist.** [client.ts:70-75](packages/excalidraw/TTA/client.ts#L70-L75) requires `revision: number`; the server returns `{ ok, chatId, updatedAt? }` (`tta-types.ts` → `ChatTruncateResponse`, `truncateTtaChat` in `tta.ts:1974-1994`). Stale field — remove it (it currently lies to every consumer of `truncate()`).
- 🟡 **M5 — Local/server divergence when truncate fails.** [TTADialog.tsx:1113-1136](packages/excalidraw/TTA/TTADialog.tsx#L1113-L1136) — on message delete, local state is truncated even if `transportAdapter.truncate` fails (only `console.warn`). The server then still holds the deleted turns and the next generation’s context includes them — invisible to the user. Either truncate locally only after server success, or surface a retryable warning. (Same applies to the missing-`turnId` skip path at 1127-1131.)
- 🟡 **M6 — Root-absolute asset URL in the library.** [TTAHistory.tsx:39](packages/excalidraw/TTA/TTAHistory.tsx#L39) (`<img src="/tta-chat-empty.svg">`) — breaks every npm consumer that doesn’t serve that file at site root. Import the SVG so the bundler inlines/fingerprints it.
- 🟡 **M7 — `assistantPreviewCache` grows without bound.** [useAIAssistantPreview.ts:50](packages/excalidraw/TTA/useAIAssistantPreview.ts#L50) — module-level `Map` keyed by message id, never evicted (entries survive chat deletion and accumulate SVG data-URLs all session). Add a small LRU cap or clear on chat switch/delete.
- 🔵 **M8 — Failed follow-up leaves the canvas empty-handed.** Once a new generation renders its first chunk, `activateCanvasDraft` removes the previous generation (`commitQueuedGenerationReplacements` → `IMMEDIATELY`); if the new generation subsequently fails, the old result is not restored (the error path only removes the new draft — [useAIStreamingLifecycle.ts:357-358](packages/excalidraw/TTA/useAIStreamingLifecycle.ts#L357-L358)). `executeDelete` already contains re-insert logic for the “latest remaining result” — reuse it on failure.

### Server

- 🟡 **M9 — A hallucinated `ttaReplace`/`ttaAfter` id fails the whole turn.** `replaceAdditiveExml` throws `Replacement target not found: #id` (`exmlAdditiveMerge.ts:573-600`); by then the full stream (and possibly an LLM fix round) has been paid for, and the user gets a generic 500 (the merge error isn’t a `TtaServiceError`, so `getTtaErrorResponse` masks it). Fall back to `op: "full"` (or append-at-end for dangling `ttaAfter`) instead of failing — the parsed fragment is valid at that point.
- 🟡 **M10 — `finishReason: "length"` isn’t acted on.** `tta.ts:2191-2194` records it, then proceeds to parse a knowingly-truncated response → near-certain parse failure → LLM fix with `FIX_TTA_TOKENS = 4096` (half the budget, likely truncating again). Detect `length` and fail fast with an actionable “too complex, simplify the request” error, or retry with a continuation rather than a repair prompt.
- 🟡 **M11 — Fix-pass token usage is dropped.** `requestTtaFix` ignores `done.usage` (`tta.ts:1552-1554`), so repaired generations under-report usage (billing/metrics blind spot).
- 🟡 **M12 — Provider error text leaks to clients.** `parseExmlWithFix` wraps `fixError.message` into a `TtaServiceError(GENERATION_ERROR)` (`tta.ts:1771-1774`), which `createStreamError` forwards verbatim — that can include raw provider/SDK messages. Whitelist parse-error messages; map everything else to the generic copy (you already do this for non-`TtaServiceError`s).
- 🟡 **M13 — OSS chats are unscoped.** `ossStoreAdapter.loadChatFilters` is `eq(table.id, chatId)` (`tta.ts:819-822`) with `auth: optional` and `owner: null` — anyone who learns a chat UUID can extend it (and read its context indirectly via additive follow-ups) or truncate it. UUIDv4 entropy is the only protection. Cheap hardening: issue a per-chat secret on creation, require it on follow-up/truncate. Also the OSS limiter is 100/day with a `FIXME: higher than prod` note — confirm before release.
- 🟡 **M14 — Data retention.** `tta_images.value` stores full data URLs (≤3.5 MB × 4/turn — `ai-schemas.ts:45`), `tta_errors.generation_text` stores entire raw responses, `truncateConversation` leaves zero-turn chat rows behind (`tta.ts:1395-1411`), and superseded message rows accumulate per retry. Verify FK cascades from `tta_chat_turns` → messages/images actually fire on truncate, and consider a TTL/cleanup job; this table set will grow fast.

Consider always attempting the first partial parse regardless of the delta floor.

## 4. Design-level suggestions (no bugs)

1. **Single-flight at the hook level.** Today “only one generation at a time” is enforced by scattered UI state (`isSendingChat`, button disabling, shortcut guards). Make `useAIStreamingLifecycle.generateResponse` itself reject/auto-cancel when a stream is active — every C1-class bug disappears structurally.
2. **Make the stream protocol self-terminating end-to-end.** The end-marker already exists server-side (`[DONE]` from `StreamingResponse.end()`); the client just ignores it. Surface it, require `done|error` for success client-side (C2), and add a heartbeat comment server-side for proxy-timeout immunity — see [tta_c2.md](tta_c2.md) §6.
3. **Status as a state machine.** `lifecycleStatus`, `progressPhase`, `statusText`, `isComplete`, `stopReason`, `error`, `warningType` overlap; several spots reconcile them by hand (e.g. `stopIncompleteAssistantMessages`, the stop handler, retry resets — [TTADialog.tsx:966-1002](packages/excalidraw/TTA/TTADialog.tsx#L966-L1002)). A single discriminated `status` union with derived render fields would remove a whole class of “forgot to reset field X” bugs (the retry reset already lists 9 fields).
4. **TTADialog.tsx is 1.4k lines.** The chat-id/updatedAt bookkeeping (`applyServerChatId`, `applyActiveChatUpdatedAt`, `updateHistoryChatUpdatedAt`, refs) wants to live inside `useTTAChatHistory`; delete/retry orchestration could be a `useTTAChatActions` hook. Mechanical split, big readability win.
5. **Server: consider persisting skeletons, not just EXML.** Every context load re-parses stored EXML per request (`parseExmlV1` on merge/partials); storing the parsed result alongside (versioned via `response_schema_version`, which already exists) would cut repeated parse cost for follow-ups.
6. **Telemetry for the repair ladder.** `logParseFixMetrics` is great; add counters for additive-op distribution (`full`/`append`/`replace`), hallucinated-target fallbacks (M9), and `finishReason=length` (M10) — these directly measure prompt quality.

## 5. Live validation (2026-06-12, dev oss-ai-server on `dwelle/tta`)

Empirically confirmed against the running OSS server (raw SSE captures via curl):

- **Wire protocol**: `started` → `partial`* → `done` → `data: [DONE]` sentinel, exactly as `StreamingResponse` reads; **no heartbeat frames** exist (C2 / [tta_c2.md](tta_c2.md)).
- **S3 confirmed**: partials are full snapshots emitted per provider delta, unthrottled on the non-additive path — a 5-element drawing produced 11 partials at 28–144 ms cadence growing 52 B → ~2 KB; the follow-up produced 18 partials → 3.2 KB.
- **Type drift confirmed**: the final partial arrives with `isComplete: true` — the signal `client.ts:256-259` hardcodes away (Low-list item in §3).
- **M4 confirmed**: truncate returns `{"ok":true,"chatId":…,"updatedAt":…}` — no `revision` field.
- **ID stability confirmed**: a follow-up generation reused 4/5 element ids from the previous turn verbatim (`tta-…` stable hashes) — the in-place-replacement design works end-to-end.
- **Context coherence**: truncate-to-turn-1 and a mid-stream client abort both left the chat usable; subsequent generations behaved correctly.
- **New observation**: a small follow-up edit (“rename box A to X”) streamed **zero** partial frames — spinner-only until `done` (see the Low-list item on the additive partial floor).
- Dev trivia: `RATE_LIMIT_ALLOW_LIST = ["127.0.0.1"]` exempts IPv4-localhost from rate limiting (no `X-RateLimit-*` headers locally); `::1` is not in the list, so IPv6-localhost *is* rate-limited — the 100/day OSS limiter was observed live via the Windows-side run.

## 6. What looks solid (keep)

- `createEagerAsyncIterable` (`tta.ts:499-569`) — overlapping provider startup with the attempt insert is a nice latency win, and the cancel semantics are correct.
- The preview commit dance ([useAIStreamingCanvasPreview.ts:108-173](packages/excalidraw/TTA/useAIStreamingCanvasPreview.ts#L108-L173)) — tombstone-with-NEVER then re-add-with-IMMEDIATELY to get correct undo granularity, with the reasoning in a comment.
- Deterministic chat-scoped id remapping (`elementIdRemap.ts` + `stableId.ts`) — enables in-place streamed updates and prevents cross-chat collisions; collision loop is bounded and correct.
- Heuristic → LLM repair ladder with metrics (`parseExmlWithFix`), and `shouldAttemptAutoFixForParseFailure` gating.
- SSE parsing ([data/sse.ts](packages/excalidraw/data/sse.ts)) — handles CRLF, multi-line `data:`, comments, trailing buffer; abort handling is careful.
- Route-level zod validation (`ai-schemas.ts`) with image count/size caps; Plus route auth + per-user rate limiting with rollback intent.
- Parser input hardening (size/depth/node caps), no dynamic code execution, URL scheme whitelisting in `embeddable.ts`.
